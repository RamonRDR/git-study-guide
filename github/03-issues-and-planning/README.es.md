**Objetivo:** Transformar solicitud en trabajo rastreable con criterios de aceptación.

## Qué y por qué

Issue registra tarea, defecto o pregunta fuera del historial Git. Labels clasifican, assignees indican responsabilidad, milestones agrupan trabajo hacia objetivo. GitHub Projects ofrece vistas y campos personalizados; estado del project no es necesariamente estado de issue. Discussions, cuando está habilitado, sirve conversaciones y preguntas de comunidad en vez de tarea de implementación requerida. Usa título claro, contexto, resultado esperado, reproducción de bugs y criterios verificables. Vincula trabajo relacionado en vez de duplicar. Cerrar issue no cambia archivos Git.

## Práctica

Offline: escribe issue #1, título Add setup note, contexto: lectores no encuentran requisitos, aceptación: README indica requisitos y una verificación segura. Asigna label ficticia documentation, milestone v0.1 y owner maintainer. Dibuja tablero Todo -> In progress -> Done. Crea borrador separado de discussion pidiendo opinión sobre orden de lecciones. Opcional: solo en sandbox privado abre issue, añade labels/milestone existentes si permitido y registra número; no mensajes externos ni funciones pagas necesarias. Déjala abierta para ejercicio PR.

## Errores comunes y seguridad

Nunca pegues secretos, datos personales ni logs internos en issues. No publiques issues de práctica en proyectos reales. Evita cerrar antes de aceptación; reabre issue de sandbox cerrada por error si hace falta.

## Ejercicio y autoevaluación

Aprueba si issue tiene resultado observable, label y milestone con fines distintos y explicas por qué discussion no es automáticamente tarea.
