**Objetivo:** Transformar solicitação em trabalho rastreável com critérios de aceitação.

## O que é e por quê

Issue registra tarefa, defeito ou pergunta fora do histórico Git. Labels classificam, assignees indicam responsabilidade, milestones agrupam trabalho rumo a objetivo. GitHub Projects oferece visualizações e campos personalizados; status do project não é necessariamente estado da issue. Discussions, quando habilitado, serve conversas e perguntas da comunidade em vez de tarefa obrigatória de implementação. Use título claro, contexto, resultado esperado, reprodução para bugs e critérios verificáveis. Vincule trabalho relacionado em vez de duplicar. Fechar issue não altera arquivos Git.

## Prática

Offline: escreva issue #1, título Add setup note, contexto: leitores não encontram pré-requisitos, aceitação: README informa pré-requisitos e uma verificação segura. Atribua label fictícia documentation, milestone v0.1 e owner maintainer. Desenhe quadro Todo -> In progress -> Done. Crie rascunho separado de discussion pedindo feedback da ordem das aulas. Opcional: só no sandbox privado, abra issue, adicione labels/milestone existentes se permitido e registre número; nenhuma mensagem externa ou recurso pago necessário. Deixe aberta para exercício PR.

## Erros comuns e segurança

Nunca cole segredos, dados pessoais ou logs internos em issues. Não poste issues de prática em projetos reais. Evite fechar antes da aceitação; reabra issue de sandbox fechada por engano se necessário.

## Exercício e autocorreção

Passe se issue tem resultado observável, label e milestone com fins diferentes e explicar por que discussion não é automaticamente tarefa.
