**Objective:** Turn a request into traceable work with acceptance criteria.

## What and why

An issue records a task, defect or question outside Git history. Labels classify, assignees indicate responsibility, milestones group work toward a goal. GitHub Projects provides views and custom fields to track work; project status is not necessarily issue state. Discussions, where enabled, serve community conversation and questions rather than a required implementation task. Use a clear title, context, expected outcome, reproducible steps for bugs and verifiable acceptance criteria. Link related work rather than duplicating it. Closing an issue does not change Git files.

## Practice

Offline: write issue #1, title Add setup note, context: readers cannot find prerequisites, acceptance: README names prerequisites and one safe verification step. Assign fictional label documentation, milestone v0.1 and owner maintainer. Draw a project board with Todo -> In progress -> Done. Create a separate discussion draft asking for feedback on lesson order. Optional: in your private sandbox only, open the issue, add existing labels/milestone if permitted, and record the issue number; no external messages or paid project features required. Leave it open for the PR exercise.

## Common mistakes and safety

Never paste secrets, personal data or internal logs into issues. Do not post practice issues to real projects. Avoid closing work before acceptance is met; reopen a mistakenly closed sandbox issue if needed.

## Exercise and self-check

Pass if your issue has an observable result, a label and milestone with different purposes, and you explain why a discussion is not automatically a task.
